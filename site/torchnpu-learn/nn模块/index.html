    Part3. 如何通过dispatch key查询真正需要定位的算子

    定位算子的流程：

    OperatorEntry 上文的 OperatorEntry 保存名称、签名和后端实现，下面看它的成员

    • name_：这个条目代表哪个算子重载，例如 aten::avg_pool2d 的默认重载。
    • schema_：这个算子接收什么参数、返回什么结果等信息。
    • dispatchTable_：各个运行时 dispatch key 对应的可调用实现数组。
    • dispatchKeyExtractor_：帮助从本次参数及执行状态中提取调度所需的 keyset。

    真正机制在后两者，我们分开聊，如果从真实的tensor计算时候调用的参数，他们配合逻辑是这样的：

    • Dispatcher::call
    • 使用dispatchKeyExtractor_提取dispatchKeySet
    • lookup(keyset) 返回表中选中的 KernelFunction
    • 把原来的 Tensor 和池化参数传给选中的KernelFunction实现

    按照顺序，先讲OperatorEntry的dispatchKeyExtractor_

    这里有 boxed 和 unboxed 两种传参入口。本例沿 unboxed 路径，直接接收前面解析出的 Tensor、整数列表和布尔值；提取器从适用的 Tensor 参数收集 key。Python Tensor 怎样取得 C++ 表示，以及 Args... 是什么，见附录。boxed 入口的含义见参数说明，参数包的语法见模板说明。

    • 这个类包含几种参数
      • DispatchKeyExtractor
      • dispatch_arg_indices_reverse_：预先存储 boxed 调用：参数栈里哪些位置需要检查
      • 其余三个字段：为 boxed/unboxed 调用记录：哪些层可以跳过，以及是否需要按后端区分
        • nonFallthroughKeys_、nonFallthroughKeysPerBackend_数组
        • bool requiresBitsetPerBackend_
        • 他们的用处会在后续详细讲解

    具体如何提取参数的运行步骤

    • 第一步：从 Tensor 收集后端、自动微分等 key（调度标记）
      • DispatchKeyExtractor getDispatchKeySetUnboxed
      • 子第一步：用 MultiDispatchKeySet 收集参数中的 key，构造一个keyset。入口见 multi_dispatch_key_set
        • 此处讲解的是较为简单的unbox方法
        • MultiDispatchKeySet
        • 将各个 Tensor 的 keyset 合并到 ts；同名处理函数的不同参数形式见附录
        • ts = ts | x.key_set();
          • unboxed 方法通过重载处理各参数，合并参与调度的 Tensor 等对象的 key_set()
        • 此处的原始 keyset 主要来自输入张量 self。池化窗口大小会影响后续计算，但不会在这一步直接决定 CPU 或 NPU
        • 多张量算子则会合并多个输入的 keyset, 设备兼容性还需要相应实现检查
      • 子第二步：结合当前线程状态，并去掉可以跳过的层
        • DispatchKeyExtractor
        • 将前面收集的 keyset 传给getDispatchKeySetFromRawDispatchKeySet
        • subsubstep1：按照当前线程状态增加、删减 keyset，见提取器中的处理代码
          • auto dispatch_keys = (ks | tls.included_) - tls.excluded_;
          • 当前线程的加入与排除状态怎样影响调度，见附录：TLS
        • subsubstep2:返回dispatch_keys & nonFallthroughKeys_ & key_mask
          • nonFallthroughKeys_:
            • 过滤 fallthrough 层：这种实现直接放行，不做额外处理
            • 如果不同后端的 fallthrough 情况不同，使用nonFallthroughKeysPerBackend_
          • key_mask：额外允许保留哪些 key；这个调用路径默认传入 FULL
    self                  Tensor         → 收集 self.key_set()
kernel_size           整数列表        → 不贡献 keyset
stride                整数列表        → 不贡献 keyset
padding               整数列表        → 不贡献 keyset
ceil_mode             bool           → 不贡献 keyset
count_include_pad     bool           → 不贡献 keyset
divisor_override      可选整数        → 不贡献 keyset

    Part5. 从 NPU wrapper 到 CANN 的 ACLNN 算子接口

    上一节讲到，m.impl 将 wrapper_NPU__avg_pool2d 接入 Dispatcher；实际调用时，再经过适配器执行这个 wrapper。现在从它的函数体开始往下看。

    wrapper 如何调用 op-plugin

    wrapper_NPU__avg_pool2d 定义在构建生成的 RegisterNPU.cpp 中，见本次找到的完整函数。它先做检查和环境准备，再把输入 Tensor 与池化参数交给 op_plugin::avg_pool2d。

    函数内部按顺序做什么？

    1. 记录并检查共同设备。 check_and_update_common_device 记录首次遇到的 Tensor 设备，后续 Tensor 与之比较，不同则报错。本例只有 self，因此主要记录 self.device()。可选值与未使用变量的写法见附录。

    2. 按开关检查输入存储是否安全。 get_npu_data_unsafe_flag() 为真时，调用 check_npu_tensor_is_safe(self)，检查 NPU allocator 对这块存储的安全标记；不安全则报错。它并不检查池化窗口大小或计算结果。

    3. 设置设备上下文。 OptionalDeviceGuard 在这里使用 self 所在设备，退出时恢复原来的设备上下文。自动恢复的机制见附录。

    4. 准备 profiler 记录。 使用 NPURecordFunction 进行性能分析相关记录；该段是否编译进程序由构建标记决定，写法见附录。

    5. 调用 op-plugin，并按需执行前后 hook。 开启 CheckOpHookEnable()（要使用hook） 时，

    6. 取得负责 hook 的对象，调用它的 PreHook，把输入和池化参数交给它，进行计算前的额外处理
    7. 再调用 op_plugin::avg_pool2d得到结果res
    8. 正常返回后执行 PostHook(res)，把res 交给计算后的额外处理入口，处理后返回结果；
    9. 未开启时直接调用并返回。

    最后两个分支都只调用一次同一个函数：

    op_plugin::avg_pool2d(
    self, kernel_size, stride, padding,
    ceil_mode, count_include_pad, divisor_override);

    这里的参数直接沿用 wrapper 收到的参数；开启 hook 时，用局部变量 res 接住返回的 Tensor，供 PostHook 使用。wrapper 本身没有分配池化输出，也没有计算平均值。

    下一步要看的就是 op_plugin 命名空间下的 avg_pool2d 函数体。

    op_plugin 如何选择池化实现

    我们在生成文件 OpInterface_19.cpp 的第 582 行找到了这个函数，见完整源码。文件前面的 namespace op_plugin { 表明，这里的 avg_pool2d 就是 wrapper 调用的 op_plugin::avg_pool2d。

    它负责选择下一层使用哪套池化实现。

    这里先认识 JIT（Just-In-Time，即时编译）：可以理解为在程序运行期间，按需要进行编译，准备设备能够执行的算子程序。这里的开关控制的是 CANN 算子的编译模式，涉及在线编译与使用已经编译好的算子二进制文件，不能与 PyTorch 的 torch.jit 混为一谈。参见 CANN 编译选项说明。附录：这里的 JIT。

    下面按执行顺序看这个函数：

    is_jit_disable 记录是否关闭了这里的 JIT 编译模式；self_base_format 记录输入 self 是否使用基础的tensor在内存中的存储格式。

    因此，这几个同名函数的职责需要区分：

    仅凭这段代码，还不能确定某次运行一定走哪条分支，需要知道当时两个条件的值。下面分别看它们的函数体，我们下面会对一些辅助函数的处理减少讲解，他其实对整体的调用链条没有什么帮助，主要是细节的改变。

    op_api：准备输出，然后调用 ACLNN

    这个实现直接写在 op-plugin 的 ops/opapi/AvgPool2dKernelNpuOpApi.cpp 中，不需要通过生成器才能看到，见完整 avg_pool2d。

    读这一层时，先区分三个名字：self 是输入 Tensor；output_size 是输出的形状，也就是每个维度多大；result 是准备用来存放计算结果的 Tensor。知道形状以后，就可以先分配存储空间，后面再把计算结果写进去。

    1. 算出输出形状。
    output_size = calc_output_size_with_generalized_attrs(
    self, kernel_size, stride, padding,
    ceil_mode, count_include_pad, divisor_override);

    此处省略了变量的类型，完整声明见源码。这个辅助函数先把池化窗口、步长和填充解释成二维参数：例如窗口 (2) 按 (2, 2) 理解，未指定步长时使用窗口大小。它也检查步长不能为零、填充不能为负等条件，再交给输出尺寸推导函数。

    例如输入形状为 [1, 1, 4, 4]（一批有几张图片、每张图片有几个通道，图片高度，图片宽度），窗口和步长都是 (2, 2)，没有填充时，输出形状为 [1, 1, 2, 2]。这一步只确定输出需要装多少数字，还没有算出这些数字。

    1. 分配输出 Tensor。
    at::Tensor result =
    at_npu::native::OpPreparation::apply_tensor_without_format(self, output_size);

    这次分配使用输入的设备、数据类型等选项，按刚算出的形状创建输出存储。此时 result 已经有空间，但池化结果还没有写入。without_format 表示这里采用普通连续存储的创建路径，不要求沿用输入的 NPU 私有存储格式。

    1. 确认当前环境提供 ACLNN 接口。
    DO_COMPATIBILITY(
    aclnnAvgPool2d,
    acl_op::avg_pool2d(self, kernel_size, stride, padding,
                       ceil_mode, count_include_pad, divisor_override));

    DO_COMPATIBILITY 是宏，可以先理解为一段放到当前位置执行的公共代码。它检查 aclnnAvgPool2d 和 aclnnAvgPool2dGetWorkspaceSize 两个接口是否能找到。接口齐全就继续往下；缺失时，如果设备允许旧实现，就调用 acl_op::avg_pool2d 并直接返回；只支持 ACLNN 的设备则报错。见完整宏。

    这是调用前的兼容检查，不表示“ACLNN 计算出错后再尝试旧实现”。即使上一层选中了 op_api，这里仍可能转入 acl_op。

    1. 把输出和参数交给执行辅助函数。
    avg_pool2d_out_npu_nocheck_opapi(
    result, self, kernel_size, stride, padding,
    ceil_mode, count_include_pad, divisor_override);
return result;

    这里把已分配的 result 传进去，让后续计算使用这块输出存储。辅助函数的名字带有 out，表示接收已有输出 Tensor；它与另一个单独的 avg_pool2d_out 函数需要区分，这个函数用于处理传入参数中带有目标输出tensor的情况，在pytorch里的对应重载aten::avg_pool2d.out。

    辅助函数里怎样发起计算？

    avg_pool2d_out_npu_nocheck_opapi先整理两个参数：divisor_override 是手动指定平均值的除数，未指定时用 0 表示采用默认规则，显式指定 0 则报错；cube_math_type 是传给底层的计算精度选项，这里先知道它作为参数继续传下去即可。

    然后执行完整的调用语句：

    EXEC_NPU_CMD(
    aclnnAvgPool2d,
    self, kernel, stride, padding,
    ceil_mode, count_include_pad,
    s_divisor_override, cube_math_type, result);

    EXEC_NPU_CMD 是负责调用 ACLNN 的公共宏，aclnnAvgPool2d 指定本次要调用的算子接口，其余内容是输入、池化参数和输出。它的内部调用步骤是后面要继续追的下一层。

    前面的形状辅助函数使用自己整理出的二维参数推算尺寸；这里仍然接收原来的参数列表，不能把推算时补齐列表理解为原参数已经被修改。

    acl_op：整理参数，再组装 AvgPoolV2 命令

    旧实现直接写在 op-plugin 的 ops/aclops/AvgPool2dKernelNpu.cpp 中，见完整 avg_pool2d。它也要先准备输出，但参数整理和执行入口与 op_api 不同。

    1. 检查参数。 avg_pool2d_parameter_check检查窗口、步长、填充的参数个数，以及输入是否为三维或四维 Tensor；本地这版代码还要求显式指定的 divisor_override 在 [1, 255] 内。

    2. 把三维输入临时按四维处理。 三维输入形状为 [C, H, W]，四维则为 [N, C, H, W]，分别表示通道、高度、宽度，以及额外的批次维度。输入是三维时，unsqueeze(0) 在开头加一个大小为 1 的维度，变成 [1, C, H, W]，方便后面的统一处理。这里的 self_copy = self 和增加维度共用原来的数据存储，并不复制整份输入数字。

    3. 补齐二维参数，算输出形状并分配结果。 窗口、步长、填充分别整理成两个数，未指定步长时采用窗口大小。然后同样调用 avg_pool2d_npu_output_size，再用 npu_preparation::apply_tensor 分配 result。这里的 npu_preparation 是 OpPreparation 的简称，分配实现见完整函数。

    4. 调用 avg_pool2d_out_nocheck 执行辅助函数。 它接收 result、整理后的输入和二维参数，继续组装执行命令，见完整辅助函数。

    5. 恢复三维输出。 如果原输入是三维，返回前用 squeeze(0) 去掉刚才临时增加的批次维度，使输出继续保持 [C, H_out, W_out] 的形式。

    辅助函数里怎样组装命令？

    at_npu::native::OpCommand cmd;
cmd.Name("AvgPoolV2")
   .Input(self)
   .Output(result)
   .Attr("ksize", kernel_size_new)
   .Attr("strides", strides_size_new);

    这里展示了命令的前几项，完整属性见源码。cmd 可以理解为一份执行请求：

    写法 在请求中记录什么
    .Name("AvgPoolV2") 要执行的 CANN 算子名称
    .Input(self) 使用哪个输入 Tensor
    .Output(result) 使用哪个输出 Tensor 存放结果
    .Attr(名称, 值) 窗口大小、步长、填充等设置
    .Run() 将组装好的请求交给执行框架

    设置名称和属性时还没有计算池化结果，最后的 .Run() 才进入执行流程。连续调用的语法见附录。

    辅助函数把窗口从 [k_h, k_w] 整理成 [1, 1, k_h, k_w]，步长也扩成四维，前两个 1 对应批次和通道维度。get_paddings则计算上、下、左、右四个填充值，并处理 ceil_mode 下的边界。

    命令还设置是否把填充位置计入平均值。代码通常用 exclusive = !count_include_pad 表达相反的开关；本地实现对 Half 和 Char 类型会将 exclusive 设为 true。最后设置除数并执行：

    到这里，两条实现的下一步就明确了：op_api 进入 EXEC_NPU_CMD(aclnnAvgPool2d, ...)，acl_op 进入 OpCommand::Run()，执行它组装的 AvgPoolV2 请求。两条路径都使用 NPU 执行接口，acl_op 并不表示转到 CPU。

    EXEC_NPU_CMD：把池化参数交给 CANN

    上一层已经分配了输出 result，现在需要让 CANN 使用输入和池化参数，向这块输出存储写入结果。先沿 V1 宏中未命中执行器缓存的主线看，其他分支见附录。

    下面始终追踪同一次池化请求：它先在宏中被包装成 acl_call，传入执行函数后叫 func；如果需要排队，又会被保存到任务对象的 customHandler 中。名称和保存位置在变化，我们要看的是这份待执行的计算怎样传下去，最后在哪一句被调用。

    这里会遇到三个新名字：

    名字 用来做什么
    workspace 计算过程中使用的临时设备内存；最终结果放在已有的 result 中
    executor 第一段 CANN 接口准备好的执行信息，第二段接口用它发起计算
    stream NPU 任务的执行通道，用来安排任务顺序

    宏内部按顺序做以下几件事：

    1. 找到两个 CANN 函数的地址。
    GetOpApiFuncAddr(#aclnn_api "GetWorkspaceSize");
GetOpApiFuncAddr(#aclnn_api);

    本例查找的是 aclnnAvgPool2dGetWorkspaceSize 和 aclnnAvgPool2d。地址由查找函数返回，后面据此调用两个接口；宏怎样组成这两个名字，见附录。

    1. 转换参数表示。
    auto converted_params =
    ConvertTypes(__VA_ARGS__, workspace_size_addr, executor_addr);

    ConvertTypes接收输入、窗口、步长、填充、输出等参数，把它们整理成 CANN 接口需要的表示。可变参数宏的写法见附录。

    对普通 NPU Tensor，这一步创建描述对象，记录形状、数据类型和已有数据的存储地址。可以理解为给 CANN 一张说明卡，告诉它“数据是什么、在哪里”，见Tensor 转换函数。

    1. 调用第一段接口，取得执行信息和临时空间大小。
    auto workspace_status = call(getWorkspaceSizeFunc, converted_params);

    这里的 getWorkspaceSizeFunc 指向 aclnnAvgPool2dGetWorkspaceSize。call 将整理后的参数交给它，CANN 把所需临时内存大小填回 workspace_size，把执行信息填回 executor。返回的 workspace_status 用来检查这次调用是否成功。

    1. 按大小分配临时空间。 如果 workspace_size 不为零，就调用 unsafe_empty_workspace(workspace_size) 分配设备内存，并取得它的地址 workspace_addr；为零则不需要分配。见分配函数。

    2. 提交计算。 前面的参数、executor 和 workspace 准备好以后，宏执行：

    OpCommand::RunOpApiV2("aclnnAvgPool2d", acl_call);

    这一句是当前计算的提交入口，两个参数分别表示："aclnnAvgPool2d" 是本次操作的名称，用于日志、性能记录等；acl_call 是交给框架执行的函数，其中写着真正调用 CANN 的代码。计算动作由第二个参数提供，不能只根据第一个字符串理解为框架会再次按名字查找算子。

    接下来先看 acl_call 写了什么，再看 RunOpApiV2 怎样执行它。注意，V1 宏也调用这个名为 RunOpApiV2 的方法，两处版本号描述的是不同层。

    acl_call：把 CANN 调用写成一个函数

    acl_call 在 V1 宏中这样创建，下面省略了流资源设置和可选清理代码，完整内容见宏源码：

    auto acl_call =
    [converted_params, workspace_addr, workspace_size, acl_stream, executor]() -> int {
        OpApiFunc opApiFunc = reinterpret_cast<OpApiFunc>(opApiFuncAddr);
        auto api_ret = opApiFunc(workspace_addr, workspace_size, executor, acl_stream);
        NPU_CHECK_ERROR(api_ret, "call " #aclnn_api " failed");
        ReleaseConvertTypes(converted_params);
        return api_ret;
    };

    acl_call 保存了本次执行所需的信息，创建时还没有运行函数体。后面调用它，才会执行下面的 CANN 调用。lambda 的方括号、捕获与返回类型，统一见附录。

    函数体依次做以下工作：

    1. 把地址解释成可调用的函数指针。
    OpApiFunc opApiFunc = reinterpret_cast<OpApiFunc>(opApiFuncAddr);

    这句准备好指向 aclnnAvgPool2d 的可调用入口，还没有执行池化。函数指针类型和转换语法见附录，完整类型定义见源码。

    1. 真正调用 CANN 的第二段接口。
    auto api_ret =
    opApiFunc(workspace_addr, workspace_size, executor, acl_stream);

    这一行调用的是 aclnnAvgPool2d，传入临时空间的地址和大小、准备好的 executor，以及执行流。输入、输出和池化设置已经在第一段准备好，第二段据此提交设备计算。两段接口的对应关系见 CANN 文档。

    1. 检查返回码。 NPU_CHECK_ERROR(api_ret, ...) 检查 CANN 调用是否成功，出错时报告错误。api_ret 是状态码，不是计算出来的 Tensor；池化结果写入前面 result 对应的设备存储。

    2. 正常返回时清理辅助资源。 ReleaseConvertTypes(converted_params) 释放转换得到的 ACL 描述等对象；完整函数还在可用时调用 ReleaseHugeMem 做清理。这里释放的是辅助资源，不表示把输入或输出 Tensor 的数据一起删掉。最后 return api_ret 把状态码交给执行框架。

    写到这里，我们已经知道这份请求被包装成了什么：acl_call 保存执行所需的信息，函数体中写着 aclnnAvgPool2d 的调用。下一步回到宏的 RunOpApiV2("aclnnAvgPool2d", acl_call)，进入 RunOpApiV2，看它怎样接收并执行这个回调。

    RunOpApiV2：决定怎样执行 acl_call

    现在回到提交语句：

    这个方法的参数为 op_name、func、sync。传进来后，op_name 对应字符串 "aclnnAvgPool2d"，func 对应刚才的 acl_call；第三个参数 sync 没有填写，采用默认值 false。

    libopapi.so：aclnnAvgPool2d 的接口在哪里

    前面在 acl_call 中真正调用 CANN 的语句是：

    auto api_ret = opApiFunc(workspace_addr, workspace_size, executor, acl_stream);

    opApiFunc 是函数指针，它指向的地址由 GetOpApiFuncAddr("aclnnAvgPool2d") 查到。现在补上这次查找与 libopapi.so 的关系。

    libopapi.so 是 CANN 提供的算子 API 动态库。可以先把动态库理解为“已经编译好、供其他程序调用的一组函数”：torch_npu 在运行时加载它，再按函数名寻找入口地址。在这里，op_plugin 准备池化参数和输出，CANN 的算子接口则接收这些信息，处理对应的计算请求。CANN 的单算子 API 文档列出了这类接口与库的关系。

    从哪句代码开始加载这个库？ 在 op_api_common.cpp:874，GetOpApiFuncAddr 有这一句：

    static auto opApiHandler = GetOpApiLibHandler(GetOpApiLibName());

    先调用 op_api_common.h:53 的 GetOpApiLibName()，它返回字符串 "libopapi.so"。这个名字再传给 GetOpApiLibHandler，后者在 70 行 执行：

    auto handler = dlopen(libName, RTLD_LAZY);

    这里的 dlopen 用来加载动态库，返回的 handler 用于后续访问这个库。此时只是取得库的访问入口，还没有执行池化。

    回到 GetOpApiFuncAddr，876 行 将库的 handler 和要找的 apiName 一起交给 GetOpApiFuncAddrInLib。进入后，在 op_api_common.h:62 执行：

    auto funcAddr = dlsym(handler, apiName);

    dlsym 的作用是按名字寻找库提供的函数。这里的名字为 "aclnnAvgPool2d"，找到的地址随 return funcAddr 返回给宏，保存为 opApiFuncAddr，再由 acl_call 转成函数指针并调用。第一段接口 "aclnnAvgPool2dGetWorkspaceSize" 也通过同样的查找过程取得地址。

    完整的 GetOpApiFuncAddr 会先检查自定义库和已加载的算子库；没有找到时才继续检查 libopapi.so，随后还可能查询功能子库。因此，上面追的是它查询 libopapi.so 的这一条路径，实际命中哪个库取决于运行环境。

    这个库为本例提供什么功能？ 对平均池化，我们关心的是成对的两个接口。

    aclnnAvgPool2dGetWorkspaceSize 接收输入、输出和窗口、步长等设置，准备本次计算所需的执行信息，返回临时空间大小和 executor。result 的描述也在这一段传入，所以输出位置已经交给 CANN。

    aclnnAvgPool2d 接收准备好的 executor、临时空间和执行流，据此发起计算。它返回的是调用状态码，计算结果使用前面指定的输出存储。这样的“先准备、再执行”是 CANN 的两段式接口约定，宏负责把两段衔接起来。

    配套教程的远端运行记录也查看了该库的动态符号，完整摘录见符号表记录：

    00000000018aad48 T aclnnAvgPool2d
00000000018af1f8 T aclnnAvgPool2dGetWorkspaceSize

    这说明那次运行环境中的 libopapi.so 提供了这两个函数；前面的十六进制数字是符号值，T 表示已定义的代码符号。符号表能确认接口存在，但不会展示函数内部的计算步骤。该记录来自已有的远端实验，本次没有重新运行它。

    请求提交后，result 怎样回到 Python

    这一段换一个追踪对象：前面看的是计算请求怎样往下传，现在看的是输出 result 怎样往上返回。先记住，result 在提交计算之前就已经创建好了，它包含输出的形状、类型以及对应的设备存储。

    先从池化辅助函数回到 op_plugin。 在 AvgPool2dKernelNpuOpApi.cpp:52，avg_pool2d_out_npu_nocheck_opapi 在执行宏之后写着：

    这里不要把 acl_call 的返回值混进来：return api_ret 把整数状态码交给执行框架；return result 才把输出 Tensor 交给池化函数的调用者。排队时，外层还可能在回调被取出执行之前就返回 Tensor，因此返回 result 本身不保证设备计算已经完成。

    另一条 acl_op 路径也返回先前创建的 result。如果输入原本是三维，函数先在 AvgPool2dKernelNpu.cpp:248用 squeeze(0) 去掉为了旧接口增加的批次维度，然后在 250 行返回输出。

    现在回到生成的 op_plugin::avg_pool2d。在 OpInterface_19.cpp:592，它写的是：

    return op_api::avg_pool2d(self, kernel_size, stride, padding,

    输出由这一句返回给 op_plugin::avg_pool2d 的调用者；走旧路径时，599 行的 return acl_op::avg_pool2d(...) 做同样的事。嵌套调用的返回语法见附录。

    再回到 wrapper_NPU__avg_pool2d，普通路径的末尾是 return op_plugin::avg_pool2d(...)，因此输出继续返回给调用这个 wrapper 的调度包装层。如果开启了 OpHook，wrapper 会先用 res 接住输出，执行 PostHook(res)，再 return res;。

    这一阶段结束在 wrapper_NPU__avg_pool2d 的返回语句：NPU 实现已经把输出 Tensor 交回调度包装层。下一步沿这些包装层的 return，返回 ATen 的 C++ 接口。

    调度包装层怎样把 Tensor 交回 ATen？ 前面调用 wrapper 的函数对象，在 WrapFunctionIntoFunctor.h:17写着：

    return (*FuncPtr::func_ptr())(std::forward<Parameters>(args)...);

    其中的函数指针对应已注册的 wrapper；wrapper 返回后，这句把 Tensor 返回给外面的适配函数。适配函数在 make_boxed_from_unboxed_functor.h:577用 return (*functor_)(...) 继续返回。

    再向外，是 KernelFunction_impl.h:108 的 callUnboxedKernelFunction，它用 return (*func)(...) 返回；随后 177 行 的 KernelFunction::call 返回这个调用结果。前面按 key 选中实现的 Dispatcher::call，在普通路径的 Dispatcher.h:836写着 return kernel.template call<Return, Args...>(...)，因此输出又回到了 Dispatcher 的调用者。

    这些 return 是在结束此前进入的函数调用，输出沿调用关系向外传递。需要自动微分时，还会经过对应的自动微分包装层；建立梯度关系的细节留到反向部分展开。

    到这里，输出已从 at::avg_pool2d 返回 Python 绑定中的 dispatch_avg_pool2d。下一阶段从绑定里的 wrap(...) 开始，把 C++ Tensor 包装成 Python 能使用的对象。

    wrap 怎样把 C++ Tensor 变成 Python Tensor？ 本地没有生成的 THPVariable_avg_pool2d，所以这里仍以真实生成器为依据。在 gen_python_functions.py:1406，生成器会写出 lambda 内的 return {dispatch_callee}(...)，而 1408 行写出外面的 return wrap(...)。对于本例，调用关系可以简化为：

    // 按生成器说明的简化示意，不是本地生成文件的原文

    这句先取得 dispatch_avg_pool2d(...) 返回的 C++ Tensor，再交给 wrap。Tensor 对应的 wrap调用 THPVariable_Wrap，下一步进入这个函数；C++ 重载的写法见附录。

    进入 python_variable.cpp:447–452，THPVariable_Wrap 又把 Tensor 交给 THPVariable_WrapWithType。这个函数在 418 行取得原来的 TensorImpl，随后通过 get_or_init 获取或建立与它关联的 Python 对象。需要新建时，429 行分配 Python 对象，再在 437 行执行：

    new (&v->cdata) Tensor(std::forward<T>(var));

    这句把传进来的 C++ Tensor 保存到 Python 对象的 cdata 中。包装后仍关联原来的 TensorImpl 和设备存储，不会把池化数据复制到 CPU；在指定位置构造对象的写法见附录。

    最后，444 行的 return obj.release() 返回 Python 对象，由 THPVariable_Wrap → wrap → THPVariable_avg_pool2d 逐层交回 Python 调用方。F.avg_pool2d 就是这个绑定函数的 Python 名称，因此它现在返回了 Python Tensor。release() 的资源管理含义见附录。

    返回方向的最后一站是 pooling.py:779 的 AvgPool2d.forward：原来的 return F.avg_pool2d(...) 把这个 Python Tensor 再返回给模块的调用者。于是用户写下的 y = pool(x)，最终让 y 接住这个输出。

    这一条前向主线到此结束：提交方向进入 CANN 的 aclnnAvgPool2d 或 aclopCompileAndExecute；返回方向经 THPVariable_Wrap 回到 Python，并在 AvgPool2d.forward 返回输出。此时用户已拿到输出 Tensor，设备计算是否完成仍取决于执行与同步状态。若继续研究设备计算，从 CANN 接口内部接着追；若继续研究训练流程，则从这个输出参与的 backward() 开始，进入自动微分阶段。
